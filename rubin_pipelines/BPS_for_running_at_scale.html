Using BPS for running Rubin pipelines at scale

  • Monitoring workflow progress

  • Pipetask log files

BPS (Batch Production Services) is a package written by the Rubin Data Management team for runnng Rubin pipelines at scale. It provides a plugin interface that allows for different workflow management systems to be used to orchestrate the execution of large numbers of pipetasks. At NERSC, we use the Parsl-based plugin, ctrl_bps_parsl. The other two supported plugins, based on HTCondor and PanDA, require external infrastructure that isn’t available for running at NERSC.

Setting up the submission environment

For running BPS at NERSC, it recommended to use the CVMFS distributions of the Rubin software, since those are kept up-to-date with the weekly releases of the Rubin stack and are available on both the login and batch nodes. In addition, the LSSTDESC:bps_parsl_sites package provides additional site configuration classes for running at NERSC (or on other slurm batch systems). Here’s a typical set up for running at NERSC:

source /cvmfs/sw.lsst.eu/almalinux-x86_64/lsst_distrib/w_2026_43/loadLSST-ext.bash
setup lsst_distrib
setup -r <path_to>/bps_parsl_sites -j
export BPS_WMS_SERVICE_CLASS=lsst.ctrl.bps.parsl.ParslService

This assumes that a local copy of bps_parsl_sites has been cloned and built following the package instructions. The BPS_WMS_SERVICE_CLASS environment variable tells bps to use the Parsl plugin instead of the default HTCondor plugin. Additional python packages can be added by modifying the PYTHONPATH environment variable. Note that the current submission environment will be replicated on the allocated compute nodes.

Example BPS yaml config file

Here’s an example bps yaml for running at NERSC that roughly corresponds to the standalone pipetask example:

includeConfigs:
  - ${DRP_PIPE_DIR}/bps/resources/LSSTCam/DRP.yaml

pipelineYaml: "${DRP_PIPE_DIR}/pipelines/LSSTCam/DRP.yaml#isr,calibrateImage"

payload:
  butlerConfig: dp2
  inCollection: LSSTCam/defaults
  payloadName: single_ccd_test
  dataQuery: >-
    instrument='LSSTCam'
    AND detector=94
    AND exposure=2025122500001

computeSite: task_vine

site:
  local:
    class: lsst.ctrl.bps.parsl.sites.Local
    cores: 128
    monitorEnable: true
    monitorFilename: runinfo/monitoring.db
  task_vine:
    class: bps_parsl_sites.SlurmTaskVine
    walltime: "05:00:00"
    qos: regular
#    walltime: "00:30:00"
#    qos: debug
    constraint: cpu
    exclusive: true
    nodes_per_block: 1
    provider_options:
      init_blocks: 1
      min_blocks: 0
      max_blocks: 5
    scheduler_options: |
      #SBATCH --module=cvmfs
      #SBATCH --account=m1727
    worker_options: "--memory=480000"  # total memory in MB
    monitorEnable: true
    monitorFilename: runinfo/monitoring.db

There are some notable differences with respect to the pipetask version:

  • The includeConfigs section at the top allows one to include other bps yaml configurations. The one listed in this example provides resource estimates for each kind of pipetask, which are based on running those tasks in production at the Rubin data facilities. Those resource estimates can include memory requirements, numbers of cores to use (for those few tasks that run in multi-processing mode), as well as additional pipetask command line arguments.

  • In the payload section, payloadName is used instead of output, since by default bps will set output = u/{operator}/{payloadName}, where operator will be username, if not explicitly over-ridden in the yaml config.

  • The computeSite and site sections, as shown in this example, are specific to the Parsl plugin.

    The computeSite entry selects between the options available under the site section. In the site section, two different computing options are defined:

    • local: This will use the cores on the local node for running the pipetasks. This is convenient for testing or if you have a smaller payload that can run on a single perlmutter batch node acquired from the interactive queue. In this example, all 128 cores on a perlmutter node have been specified.

    • task_vine: This uses the TaskVine-based executor available in Parsl for distributing the jobs to the workers. The TaskVine executor uses the resource information, i.e., the memory and CPU requests provided in ${DRP_PIPE_DIR}/bps/resources/LSSTCam/DRP.yaml, to pack the worker nodes based on the available resources.

Scaling up to multiple nodes

There are several settings in the task_vine site example above that are relevant for making effective use of the NERSC batch resources.

  • walltime and qos: For testing configurations, using qos: debug and walltime values up to 30 mins (“00:30:00”) will provide quick turnaround time in the queues. For production runs using qos: regular, one can choose walltime values corresponding to the queue with the shortest wait time, as long as the requested time is longer than the longest anticipated job run time. The Parsl plugin will continue submitting slurm worker jobs until the processing is finished.

  • exclusive: true: This ensures that whole nodes are allocated.

  • nodes_per_block: 1: Parsl defines workers in terms of “blocks”, which can consist of multiple nodes per block in order to support MPI processing across multiple nodes. Since the Rubin code does not use MPI, this should be set to 1.

  • provider_options: Here init_blocks is the initial number of blocks to schedule, and min_blocks and max_blocks give the range of the number of blocks that Parsl will use for processing. For example, if you would like your workflow to use as many as 100 nodes for processing, but can still do useful work with fewer, then set min_blocks: 0 and max_blocks: 100. Parsl will submit 100 single-node batch jobs, and as each slurm job starts, it will start scheduling pipetask jobs to that worker. As the number of pipetask jobs start to wind down, the slurm worker jobs will timeout, and Parsl will only submit additional batch jobs as needed in order to process the remaing pipetask jobs.

  • worker_options: "--memory=480000": This can be used to set the amount of memory (in MB) per node to use for running pipetasks. Since each perlmutter node nominally has 512 GB of memory, it’s recommended to set this to a somewhat smaller number to provide some head room for jobs that may use more than their requested memory and to reserve memory for system resources.

Submitting a workflow

After setting up the submission environment on a NERSC login node and preparing the bps submission yaml, the following command can be used to submit the workflow:

$ (bps submit <bps_yaml_file> 2>&1 | grep -v ^parsl.process_loggers | grep -v ^monitoring_) &> bps_submission.log &

The pipes through grep filter out some noisy Parsl logging that cannot be suppressed without also suppressing the more informative bps logging info. Redirecting to a log file and running in background allows one to disconnect from the login node after submitting.

Monitoring workflow progress

The bps submission process will write to two subfolders in the submission directory: the submit folder will contain information from bps on the configuration and state of the workflow, and the runinfo folder will contain logging information from Parsl as well as the sqlite monitoring database that keeps track of the state of the individual pipetask jobs. Note that the monitorEnable and monitorFilename entries in the site configs above need to be set exactly as shown for workflow monitoring to work.

To find information on all of the workflows that are being tracked in a given submission directory, the bps_report command can be used:

$ bps_report --list
Available workflows:
                                 run_id                                      workflow_name                  time_began  tasks_completed_count
0  2d89e3d5-5eca-4435-a1af-9bb56301b1aa  u_jchiang8_dp2_anacal_systematics_20261027T163...  2026-10-27 09:40:46.785110                     77

This will list all of thew workflows in the monitoring database. To get information on the status of any particular workflow, one can do, e.g.,

$ bps_report --run_id 2d89e3d5-5eca-4435-a1af-9bb56301b1aa
--run_id=2d89e3d5-5eca-4435-a1af-9bb56301b1aa
task_type               pending   launched    running  exec_done     failed   dep_fail      total
buildCellSystematics          0        221          2         77          0          0        300

where <run_id> is given in the table of runs from the bps_report --list command.

Pipetask log files

Each pipetask generates log output, and for running under bps, that output is captured in log files with extensions .stderr in the local submit directory tree. For the example bps yaml shown above, those log files would be in

submit/u/<username>/single_ccd_test/<timestamp>/logs/<pipetask_name>/<data_dimension_subfolders>

Here <timestamp> would be something like 20261027T163952Z, and <pipetask_name> would be isr or calibrateImage. The <data_dimension_subfolders> may include subfolders organized by data dimensions, such as detector, visit, patch, or tract.
